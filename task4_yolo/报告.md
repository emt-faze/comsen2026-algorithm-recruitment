## 三、图片推理结果

对 `example/` 下三张 COCO 图片推理（置信度阈值 0.25）：

| 图片 | 检出目标数 | 说明 |
|---|---|---|
| coco-bear.jpg | 0 | 未检出（图中是熊，不属于 Drone/Bird 训练类别） |
| coco-bus.jpg | 2 | 均判为 Drone，置信度 0.6365 与 0.5458 |
| coco-person.jpg | 0 | 未检出 |

**这里出现了一个值得分析的现象**：`coco-bus.jpg` 里检出的两个框并不是无人机，
而是**建筑物和背景区域**（见 `outputs/yolo_coco-bus_drone.jpg`）。
原因是该模型只在「无人机 / 飞鸟」两类数据上训练过，
它的输出空间里**没有「汽车」「建筑」这些类别**，
所以遇到画面中的高对比度物体时，只能强行归到已有类别里，
于是出现了「把楼顶框成 Drone」的误检。

这正好印证了题目背景里说的：传统 OpenCV 方法在复杂场景下效果差，
但**换成 YOLO 也不是一劳永逸**——模型的类别空间必须覆盖实际场景，
否则会出现「越权分类」。实际部署时需要：
1. 用包含目标类别的数据训练，或
2. 提高置信度阈值 + 加入类别过滤，或
3. 在检测后接一个分类器做二次判别。

## 四、视频推理结果

对 `example/example.mp4`（1920×1080，24 FPS，378 帧，15.8 秒）逐帧推理：

| 指标 | 数值 |
|---|---|
| 处理帧数 | 378 |
| 纯推理耗时（平均） | **25.85 ms/帧** |
| 推理耗时 P50 / P95 | 25.49 / 29.80 ms |
| **推理速度** | **38.68 FPS** |
| 平均每帧目标数 | 2.81 |
| 累计检出 | Drone 226 次，Bird 832 次 |

纯推理速度 38.68 FPS **高于**视频本身 24 FPS，
说明在纯 CPU（i5-12400F）上也能做到实时处理，不需要 GPU。

结果视频：`outputs/yolo_example_drone.mp4`

**视频中的典型问题**：画面中央的无人机能被稳定框住（Drone，置信度约 0.51），
但同时**整个画面会被误检为一个巨大的 Bird 框**（置信度约 0.45）。
原因是背景是玻璃幕墙建筑，纹理被模型误认为「鸟群/飞行物」。

### 置信度阈值的影响

为量化这个问题，在视频中均匀采样 63 帧，扫描不同阈值：

| 置信度阈值 | 总检出 | 每帧目标 | Drone | Bird |
|---|---|---|---|---|
| 0.10 | 279 | 4.43 | 53 | 226 |
| 0.25 | 181 | 2.87 | 40 | 141 |
| 0.40 | 126 | 2.00 | 27 | 99 |
| 0.50 | 89 | 1.41 | 22 | 67 |

结论：
1. 所有阈值下 **Bird 的数量都是 Drone 的 3 倍以上**，说明误检主要来自 Bird 类
2. 阈值从 0.10 提到 0.50，总检出减少 68%，但 Drone 也从 53 降到 22，**真实目标同样在丢失**
3. 单帧测试中阈值提到 0.60 时，连无人机本身都检不出来了

所以**单纯调高阈值不是好办法**——这个权重对无人机的置信度本身就偏低（约 0.5），
阈值调高会先把真目标过滤掉。更合理的做法是：
- 用更多无人机数据继续训练，提升该类别的置信度
- 或者降低阈值 + 用轨迹连续性（跟踪）过滤瞬时误检

## 五、模型导出与速度对比（提高部分）

把 `drone.pt` 导出为 ONNX（opset 12，输入 640×640），
在同一批 48 帧上做公平对比（均含预热）：

| 后端 | 模型大小 | 平均耗时 | 推理速度 | 每帧目标数 |
|---|---|---|---|---|
| PyTorch (.pt) | 5.49 MB | 29.48 ms | **33.92 FPS** | 2.83 |
| ONNX Runtime (CPU) | 10.57 MB | 37.23 ms | 26.86 FPS | 3.54 |

**结果分析**：

1. **ONNX 在本机反而更慢（26.86 vs 33.92 FPS）**，这是正常现象，不是导出失败：
   - ONNX Runtime 在纯 CPU 上默认用 `CPUExecutionProvider`，
     缺少针对 x86 的深度优化（如 OpenVINO、oneDNN 的图融合）
   - PyTorch 的 CPU 推理已经用了 MKL-DNN 优化，小模型上优势明显
   - ONNX 的价值在于**跨平台部署**和**接入专用加速器**，
     在 NVIDIA GPU 上配 TensorRT、在 Intel CPU 上配 OpenVINO 才能体现收益

2. **ONNX 文件更大（10.57 vs 5.49 MB）**：`.pt` 是 PyTorch 的序列化格式（含压缩），
   ONNX 保存的是完整的计算图 + 权重，包含更多元信息

3. **fp16 / int8 量化未完成**：本机为纯 CPU 环境，无 CUDA，
   `TensorRT` 不可用；ONNX Runtime 的 INT8 静态量化需要校准数据集，
   且 CPU 上 `QuantizeLinear` 算子收益有限。这一项如实标注为**未完成**。

## 六、结论与改进方向

**已完成**：图片推理、视频推理、FPS 与模型大小指标、ONNX 导出与后端对比。

**主要发现**：
1. YOLO11n 在 CPU 上即可达到 38.68 FPS，满足 1080p 实时检测
2. 该权重类别空间只有 Bird/Drone，遇到其它物体会产生「越权误检」
3. 无人机置信度偏低（约 0.5），单纯提高阈值会误伤真目标

**改进方向**：
1. **补训练**：用题目提供的数据集（train 3893 / valid 649 / test 196）在 `drone.pt` 基础上微调，
   提升 Drone 类的置信度与召回
2. **多尺度推理**：`imgsz` 从 640 提到 960，改善小目标（远距离无人机）检出
3. **加跟踪**：用 ByteTrack / BoT-SORT 把逐帧检测串成轨迹，
   用轨迹长度过滤瞬时误检
4. **量化加速**：在 GPU 环境下导出 TensorRT FP16，或对 ONNX 做 INT8 静态量化，
   预期可获得 1.5~3 倍加速
